# ML

Exploratory/educational notebooks for Solvent's forecasting models, plus the
flat CSV some of them train on. **This is not where the production models are
canonically trained** - that's `python -m backend.forecaster.train` from the
repo root, which reads live from Postgres and persists both the `.joblib`
artifacts (`ML/notebooks/artifacts/`) and the validation metrics
(`docs/metrics.md`) that the API and dashboard actually serve.

Two distinct notebooks live here - don't confuse them:

```
ML/
  data/
    base_transactions.csv       # synthetic base_transactions export, expanded for volume (see below)
  notebooks/
    model_a_days_to_settle_training.ipynb          # Model A (per-transaction days_to_settle): mirrors backend/forecaster/train.py cell-by-cell
    daily_gmv_refund_settlement_experiments.ipynb  # exploratory: daily-aggregate GMV/refund/settlement forecasting
    artifacts/                                     # trained artifacts (gmv.joblib, model_a_*.joblib, model_b_*.joblib) - same files backend/config.py's MODELS_DIR points at
```

- **`model_a_days_to_settle_training.ipynb`** exists so the exact same
  training run backend/forecaster/train.py performs for Model A - same
  algorithm, same feature set, same `random_state`/`test_size` - can be
  opened, read, and re-executed cell by cell in Jupyter, independent of a
  running Postgres instance. (Model B's fee/refund-split training isn't
  separately mirrored here; `backend/forecaster/train.py` is the reference
  for it.)
- **`daily_gmv_refund_settlement_experiments.ipynb`** is a separate,
  genuinely exploratory notebook: three *daily-aggregate* LinearRegression
  experiments (next-day GMV, refunds, net settlement) validated against this
  folder's CSV. One of the three (GMV) beat its naive baseline and was
  productionized as `backend/forecaster/gmv.py`, retrained against Postgres
  with the same feature recipe. The other two (refund, settlement) performed
  worse than a naive previous-day baseline and were deliberately **not**
  deployed - see `backend/forecaster/refund_baseline.py` /
  `settlement_baseline.py` and `docs/metrics.md` for what ships instead. This
  notebook is not re-run by the app and isn't the source of any artifact the
  API serves.

## `base_transactions.csv` - data volume and basis (regenerated 2026-09-02)

**100% synthetic, 2,250 rows.** Earlier versions of this file blended in 7
real Razorpay test-mode payments - that's gone: the production pipeline was
fixed (see `docs/metrics.md` Stage 1) to keep real test-mode data out of any
scored/trained batch entirely, since a real payment's true labels aren't
independently knowable the way an injected synthetic label is. This CSV
follows the same rule.

Generated with one call:

```python
from backend.ingestion.synthetic_data_generator import generate_base_transactions
rows = generate_base_transactions(n_synthetic=2250, seed=42)
```

`seed=42` and the default `start_date`/`end_date` window
(`2025-06-01`..`2025-08-31`) are the same ones `run_ingestion.py` uses for the
live 250-row production dataset - this isn't a separate/different generative
model, it's a **larger draw from the identical one**. Verified by direct
comparison: generating with `n_synthetic=250` (production's actual volume)
and diffing against a live Postgres export reproduces every field exactly,
row for row, txn_id for txn_id (the only new field, `fee_amount_pending`,
didn't exist in Postgres at the time of that check but is generated by the
same deterministic per-txn RNG either way). Extending to 2,250 costs nothing
in fidelity - it's the same function, same seed, more draws.

**Row order - read this before assuming it matches Postgres.** The generator
sorts its output by `created_at` before returning
(`synthetic_data_generator.py`'s `generate_base_transactions`). At
`n_synthetic=250` that produces one date-ordering; at `n_synthetic=2250` the
extra rows interleave throughout the same `2025-06-01`..`2025-08-31` window,
producing a *different* date-ordering - so **the first 250 rows of this CSV
are not the same 250 rows, in the same order, as today's production
Postgres export**, even though the underlying generative model is identical.
If you need the exact production slice in its exact order (e.g. to reproduce
`docs/metrics.md`'s numbers by hand), use the Postgres export command below
instead of slicing this file.

`fee_amount_pending` (~2% of rows, `36/2250` here): a deliberately-injected
data gap - the gateway hasn't computed/swept the fee yet for that row. See
`docs/metrics.md` Stage 3 for why this field exists (it's what gives the tax
matcher's LLM fallback tier something genuine to resolve).

## Running

```bash
source .venv/bin/activate       # repo-root venv; needs pandas, scikit-learn, matplotlib, joblib
pip install jupyter ipykernel   # only needed to open/execute the notebooks interactively
jupyter notebook ML/notebooks/
```

`model_a_days_to_settle_training.ipynb`'s baked-in output was last executed
against the current 250-row production dataset (via a Postgres export, see
below) and matches `docs/metrics.md`'s Model A numbers. Re-running its cells
top to bottom will re-fit against whatever is currently in
`ML/data/base_transactions.csv` and may produce different numbers if that
file has changed size/seed since.

`daily_gmv_refund_settlement_experiments.ipynb`'s baked-in output reflects
the 2,250-row expanded CSV described above (GMV naive-baseline MAE ≈
₹115,860.80 vs. LinearRegression MAE ≈ ₹87,993.95 - an ≈24% improvement;
refund and settlement LinearRegression both underperformed their naive
baselines, see the notebook's own intro cell for the full comparison table).

To get the exact current production dataset instead of this expanded CSV
(e.g. to reproduce `docs/metrics.md`'s exact numbers, or after re-running the
pipeline with different synthetic data):

```bash
python -c "
import pandas as pd
from backend import db
rows = db.load_base_transactions()
cols = ['txn_id','source','razorpay_payment_id','order_id','txn_amount','payment_method',
        'created_at','day_of_week','is_weekend_or_holiday','merchant_category',
        'had_dispute_flag','had_refund','refund_amount','gst_on_fee_flag','fee_amount',
        'fee_amount_pending','tax_on_fee','fee_pct','days_to_settle','deduction_pct',
        'settled_at','status','true_tax_category']
pd.DataFrame(rows)[cols].to_csv('ML/data/base_transactions.csv', index=False)
"
```

Row order matters if you want a fresh export to reproduce `docs/metrics.md`'s
exact numbers: `train_test_split`'s row-to-split assignment depends on input
row order for a fixed `random_state`, and the command above preserves
Postgres's default read order (insertion order, i.e. `created_at`-sorted at
production's current 250-row volume) for exactly that reason.

See [`../docs/metrics.md`](../docs/metrics.md) and
[`../docs/forecaster_diagnostics.md`](../docs/forecaster_diagnostics.md) for
the production-run numbers and the fuller root-cause writeup.
